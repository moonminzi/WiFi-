# NagoTun 엔진

NAGO VPN의 WireGuard 엔진. NordSecurity의 [NepTUN](https://github.com/NordSecurity/NepTUN)
(Cloudflare BoringTun 포크, BSD-3-Clause)을 rev `ce185155e1639403cc40e01260d0830065a49555`(neptun 2.2.3)에서
가져와 우리 서버(AWS)와 폰에 맞게 고쳤다. 라이선스는 [LICENSE.md](LICENSE.md) 그대로.

- 크레이트 이름 `nagotun_engine`, 버전 `2.2.3-nago.1`. `NagoTun/`(C·JNI 인터페이스)이 `engine`으로 쓴다
- 암·복호화(ChaCha20-Poly1305)는 `ring`(ARM 어셈블리) 그대로 — 여기서 더 짜낼 게 없다

## 바꾼 것

| # | 무엇 | 왜 | 어디 |
|---|---|---|---|
| 1 | **패킷을 이벤트 루프에서 바로 처리**(`DeviceConfig::inline_packets`) — 안드로이드·리눅스도 애플처럼 | NepTUN은 애플 밖에서 tun→작업 스레드→UDP, UDP→tun 작업 스레드로 패킷마다 스레드를 넘긴다. 폰 속도에서는 스레드를 깨우는 비용이 암호화보다 크다 | `device/mod.rs`, `device/packet_workers.rs` |
| 2 | **이벤트 루프 하나일 때 읽기 이벤트를 레벨 트리거로**(epoll ONESHOT·다시 켜기 없음) | 깰 때마다 `epoll_ctl` 하나 덜. 루프가 둘 이상이면 NepTUN 그대로 | `device/epoll.rs` |
| 3 | 빈 묶음으로 tun 작업 스레드를 깨우지 않음 | 작업 스레드 모드에서 헛깨움 | `device/mod.rs` |
| 4 | IPv6가 없는 커널에서도 뜸(v6 소켓 대신 쓰지 않는 v4 소켓) | 벤치 VM 등. 폰에서는 늘 v6 소켓이 있다 | `device/mod.rs` |

앱 쪽 기본값도 같이 바꿨다: **이벤트 루프 1개**(iOS·안드로이드), 안드로이드는 바로 처리(작업 스레드 없음).
iOS 관리자용 settings → loops에서 2로 바꿔 비교할 수 있다.

### 일부러 안 바꾼 것

- **MTU 1420 그대로.** 우리 서버(AWS)는 IPv4라 바깥 헤더가 60바이트뿐이어서 1440도 들어가지만,
  한국 통신사 LTE/5G는 IPv6망이라 iPhone이 IPv4를 IPv6로 감싸서(464XLAT) 보낸다. 그러면 20바이트가 더 붙어
  1440이면 1500을 넘어 조각나거나 버려진다. 1420은 그 경우까지 들어간다(얻는 건 1.4%뿐).
- **keepalive 25초 그대로.** AWS 쪽엔 NAT가 없지만 폰 쪽 통신사 NAT가 UDP를 30초~몇 분이면 잊는다.

## 벤치(tools/nagotun-bench)

리눅스 네트워크 네임스페이스에 클라이언트(이 엔진, 안드로이드와 같은 경로)와 서버(wireguard-go)를 두고,
그 사이 UDP 중계가 왕복 시간·대역폭·병목 대기열을 흉내 낸다. iperf3 4스트림 10초, 받는 중 핑, 그리고
**엔진 프로세스의 1GB당 CPU초**(배터리·발열에 바로 걸리는 숫자). 엔진은 코어 2개에 묶고(폰의 큰 코어처럼)
서버·중계·iperf3는 다른 코어 2개에서 돈다(`CLIENT_CPUS=0,1 OTHER_CPUS=2,3`).

```
sudo tools/nagotun-bench/bench.sh <클라이언트 바이너리> [왕복ms] [대역폭Mbit] [초] [루프 수] [스트림] [대기열 0=바로 처리]
```

### 안드로이드: NepTUN 방식(루프 4 + 작업 스레드) → NagoTun(루프 1, 바로 처리)

| 조건 | 속도(받기/올리기) | 1GB당 CPU초(받기/올리기) |
|---|---|---|
| 무제한 | 702/558 → **790/612 Mbps** | 9.7/11.5 → **5.9/7.0** (−39%) |
| 왕복 30ms · 100Mbps(LTE) | 93/92 → 93/93 | 32.9/37.5 → **18.7/20.9** (−43%) |
| 왕복 130ms · 300Mbps(미국) | 251/249 → 251/248 | 22.2/21.8 → **10.4/11.3** (−50%) |

### iOS와 같은 처리 방식에서 루프 2 → 1

| 조건 | 속도(받기/올리기) | 1GB당 CPU초 |
|---|---|---|
| 무제한 | 753/688 → 773/657 Mbps | 8.9/8.1 → **6.2/6.9** |
| 왕복 30ms · 100Mbps | 93/93 → 93/93 | 26.4/26.6 → **18.0/20.7** (−22~32%) |
| 왕복 130ms · 300Mbps | 249/244 → 244/257 | 17.2/14.7 → **11.8/11.0** (−25~32%) |

속도는 병목(회선)이 정하니 같고, 같은 속도를 내는 데 드는 CPU가 준다. 루프가 여럿이면 패킷마다 다른 코어를
깨우고 같은 피어 잠금(`Mutex<Tunn>`)을 올리기·내리기가 다툰다(strace에서 `sched_yield`가 초당 수천 번).

iOS는 kqueue라 위 숫자는 같은 구조(바로 처리)를 리눅스에서 잰 것이다. 폰에서는 앱의 speed test로
loops 1과 2를 바꿔 가며 속도를 비교해 볼 수 있다(CPU는 설정 → 배터리 사용량으로).
